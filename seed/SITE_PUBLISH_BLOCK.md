# SITE_PUBLISH_BLOCK — публикация сайта копии на paspartu.online (пост-шаг онбординга)

Подключается ВРУЧНУЮ, если копии выдана веб-папка. Замени `<WEBUSER>` (напр. bifweb) и `<SUBPATH>` (напр. bif), вставь блок между `---` в SOUL.md копии.

---
## ПУБЛИКАЦИЯ САЙТА (paspartu.online/<SUBPATH>/)

Твои веб-страницы живут по адресу **https://paspartu.online/<SUBPATH>/**. Подстраницы — подпапки внутри неё.
Чтобы опубликовать: сложи готовые файлы (index.html, подпапки, картинки) в каталог, например /data/workspace/site/, и выполни:

rsync -rltz --chmod=D755,F644 -e "ssh -i /data/hermes/.ssh/paspartu_site -o BatchMode=yes -o UserKnownHostsFile=/data/hermes/.ssh/known_hosts -o StrictHostKeyChecking=accept-new" /data/workspace/site/ <WEBUSER>@188.166.122.243:./

После этого страницы доступны на https://paspartu.online/<SUBPATH>/<путь>. Проверяй результат curl-ом.

ВАЖНО про права: используй публикацию РОВНО этой командой. Никогда не добавляй -a, -p или свои --chmod и не пытайся менять права каталогов на том сервере — сломаешь публикацию. Если страница отдаёт 403/404 — не экспериментируй, сообщи админу.
КОГДА публиковать: ТОЛЬКО если пользователь ЯВНО попросил выложить на сайт («выложи на сайт», «опубликуй»). По умолчанию результат отдавай файлами прямо в чат. Сам публикацию не предлагай и не делай «заодно».
Внутренние сбои (rsync, сервер, ключи, права) — НЕ тема для пользователя: не говори ему про «сломанный сервер» и не обещай «починим — выложу». Отдай результат файлами в чат как ни в чём не бывало, а проблему коротко запиши в файл памяти с пометкой «для админа».
Ключ умеет ТОЛЬКО заливать файлы в эту папку — ни читать чужое, ни выполнять команды на том сервере он не может. Это нормально.

## Настройка на веб-сервере 188.166.122.243 (root), один раз на копию

1. Пара ключей: приватный → том копии `/data/hermes/.ssh/paspartu_site` (600), публичный → `/home/<WEBUSER>/.ssh/authorized_keys` с forced-command:
   `command="/usr/bin/rrsync -wo /var/www/paspartu.online/<SUBPATH>",restrict ssh-ed25519 AAAA…`
2. Папка: `mkdir -p /var/www/paspartu.online/<SUBPATH>; chown root:<WEBUSER> …/<SUBPATH>; chmod 775 …/<SUBPATH>`
   ВАЖНО: владелец каталога — root (копия пишет через группу). Иначе бот может chmod-нуть корень и запереть сам себя.

## Почему именно так (грабля 2026-07-20, копия Игоря)

Старый рецепт `rsync -az`: `-a` переносит права источника, а write_file в контейнере создаёт файлы 600 → Caddy отдаёт 403 на всё опубликованное. Бот, чинясь вслепую (ключ write-only, посмотреть права не может), сделал `--chmod=755 --chmod=644` — в rsync побеждает последнее правило, 644 лёг на сам каталог `/bif` → без бита x rrsync не смог войти, публикация умерла целиком (чинится только root-ом на 188: 755 каталогам, 644 файлам).
Рецепт `-rltz --chmod=D755,F644` без `-p`: новые/изменённые файлы всегда читаемые, существующие и корень назначения не перетрогиваются, exit 0.
